# Doris Query Workflow

这个 Skill 用于业务取数，不是通用 SQL 教程。它要求 Agent 在报数字之前先回答“这个数字代表什么、来自哪里、按什么粒度和时间计算”，然后才生成并执行 Doris SQL。

## 权威顺序

按以下顺序处理冲突：

1. 当前用户本轮明确的日期、货主、SKU、仓库、渠道、单位、粒度和排除条件。
2. 当前发布版本的 `metrics/*.yaml` 与 `sources/**/*.yaml`。
3. 当前发布清单中的规则、模板和黄金问题。
4. `knowledge/source-project/`、历史 SQL、用户粘贴的 SQL 和旧报表，只能作为候选证据，不能自动覆盖已发布合同。

如果用户明确要求旧口径，记录为本轮选定的 `variant`，不要把旧口径改写成默认口径。没有明确选择时，不能用相似度或旧问题上下文替用户选择变体。

## 每轮取数的固定流程

### 1. 解析请求

先提取并单独列出：

- 指标或事实：销售出库、在库、可用、在途、占用、入库、订单、退货、周转等。
- 维度和粒度：日期、仓库、货主、SKU、客户、订单、渠道、人员；明确是明细、日汇总、SKU 汇总还是仓库汇总。
- 时间窗口：自然日、月份、滚动 N 天、截至某一时刻；相对日期按 `Asia/Shanghai` 计算。
- 单位：EA、箱、KG、吨、金额、单量；确认分子和换算关系。
- 范围：用户未提及的货主、SKU、仓库、渠道、单位和粒度均为本轮 `ALL`，不得沿用上一轮。
- 输出：表格、明细、总数、排名、Excel/PNG 还是仅自然语言结论。

商品名称解析：用户说的是商品简称或展示名称时，不能把整句话直接作为
`sku_name = 用户原文`。名称可能省略规格、版本、工厂、区域或包装后缀。
应先用最小的主数据查询解析规范化 SKU 候选、商品名称、货主和产品分组，
再用 SKU 编码集合查询事实表；如果候选不止一个，结果粒度保留 SKU，或一次性
返回可选择的规格项。成品、原料和包材必须按已发布指标合同区分，不能仅凭名称
相似度选一个，也不能把解析不到名称误报为无数据。

时间统一编译为左闭右开区间 `[start_inclusive, end_exclusive)`。例如“昨天”是昨天 `00:00:00` 到今天 `00:00:00`，不要用带时间字段的 `BETWEEN` 造成边界重复或漏数。

### 2. 建立指标合同

执行前形成一份内部决策记录，至少包含：

`metric_definition`、`variant`、`source_tables`、`join_keys`、`fact_grain`、`result_grain`、`time_field`、`time_window`、`measure_field`、`unit_conversion`、`exclusions`、`freshness`、`reconciliation`。

只从与请求相关的指标和来源 YAML 读取候选，检查：

- 指标定义是否与用户说法一致。
- 事实表、维表、状态字段、逻辑删除字段是否存在。
- Join 是否会改变事实粒度。
- 用户要求的“出库”“订单”“销售数量”究竟对应出库明细、销售订单明细还是汇总宽表。
- 数量是 `ship_qty`、`allocate_qty`、`request_qty`、`received_quantity` 还是其他字段。
- 是否要排除辅料、社区团购、地配、样品、内购、取消单、逻辑删除数据等。
- 结果是否需要与总量、分项、库存组成或业务系统进行对账。

如果有两个或以上合法口径，返回一次性完整的结构化选择题，列出差异和影响，不要逐个追问，也不要猜。

### 3. 设计查询粒度

先确定事实粒度，再做汇总：

- 明细结果通常保留事实单号、行号、SKU、数量、时间和必要维度。
- 订单数使用 `COUNT(DISTINCT order_code)`，不能在一对多明细 Join 后直接 `COUNT(*)`。
- 单量、SKU 数、客户数和数量必须分别明确去重键。
- 先在事实表按唯一键聚合，再连接一对多维表；客户、SKU、仓库、枚举等维表如果不唯一，先去重或聚合。
- 一个销售订单可能对应多个出库单或多个退货单。退货按“销售订单 + SKU”汇总后再回连，不能直接把退货明细 Join 到订单明细造成倍增。
- 同一仓库、SKU、货主的库存也可能有多个批次或库存状态，必须按指标合同规定的库存状态聚合。
- 结果粒度必须与最终输出一致：凡是用于 `GROUP BY` 拆分结果的货主、仓库、SKU 或渠道，必须出现在最终表格中，或在最外层再次聚合到用户要求的粒度。不能按货主分组后隐藏货主再声称是仓库汇总。
- 维表关联必须先形成“一业务键一行”的候选关系；`DISTINCT (业务键, 名称)` 不等于按业务键去重。若同一编码对应多个名称，保留规格变体或澄清，禁止让维表 Join 倍增事实数量。
- 用户要求按仓库或其他业务维度汇总时，优先输出维护的名称/描述，不得只返回编码并把编码标成名称；编码只在用户明确要求或名称无法唯一识别时作为辅助列。名称关联必须先收敛到一业务键一行，不能因维表多行放大事实数量。
- 如果来源同时有 `wms_code` 和 `wms_desc`，仓库结果必须选择已核验的 `wms_desc` 作为仓库名称，并在聚合前完成一键一名去重；只返回 `wms_code` 不算可交付的仓库名称结果。
- 比例和占比必须在同一统计范围、同一粒度先汇总分子与总量，再用分子除以同范围总量；不能用行数作分母、不能对已四舍五入数再计算，也不能省略用户要求的占比列。未配置的分类必须单独保留。
- 占比列统一使用 `数量占比`/`占比（%）` 等业务表头，百分比值使用 0-100 刻度；双期间比较统一输出两段数量、两段日均量和 `日均变化率`，按各自完整自然日数计算，首段日均为零用 `分母为零`，无记录不得写成 0。
- 双期间列名固定为 `期间一出库数量`、`期间一日均量`、`期间二出库数量`、`期间二日均量`、`日均变化率`；具体日期写入说明，不要把日期拼进列名导致结果协议无法识别。

### 4. 生成 Doris SQL

模型可以生成任意单条只读查询，但必须满足这些基本约束：

- 只能是一条 `SELECT` 或 `WITH ... SELECT`。
- 所有物理表都使用完整的 `catalog.schema.table` 或项目允许的完整 Schema 表名。
- 只能通过 `doris_query_agent.query_doris_sql` 执行；不要用 shell、业务库、浏览器或其他连接方式补查。
- 不生成 DDL、DML、DCL、`OUTFILE`、锁、会话变量、递归 CTE、外部表函数或未知副作用函数。
- 日期使用半开区间，避免对时间列使用 `DATE_FORMAT(column)` 作为过滤条件，除非合同明确要求按日期转换。
- 逻辑删除、业务状态、货主、SKU、仓库和渠道过滤必须有证据；不能为了“查出数据”随意放宽。
- `LEFT JOIN` 不能掩盖关键事实缺失。关键关系缺失时，应在结果中提示或阻断，而不是静默补零。
- `COALESCE` 只用于合同允许的缺失值处理；不要用 `GREATEST(..., 0)` 擅自把异常负数改成零。
- 不为满足展示而新增未经用户要求的业务字段；计算字段要注明单位和公式。

如果预先无法知道最终返回列，允许使用最小业务计划：`kind + sql + purpose`。宿主根据真实 Doris 返回的列生成中性展示；如果模型声明了 `result_id/result_title`，则必须同时声明准确的 `result_columns`，且不得伪造列名、单位或结果。

### 5. 执行与状态判断

查询结果只有真实 Doris 执行成功后才能称为业务结果。严格区分：

- `clarification`：口径、范围或单位不完整，需要用户选择。
- `backend_rejection`：SQL 被只读 AST、Schema/Catalog、长度、超时或行数策略拒绝。
- `query_failure`：Doris 执行失败、字段不存在、连接失败或权限失败。
- `timeout`：超过查询时间限制，不能当作“无数据”。
- `truncated`：达到返回行数或响应大小上限，必须明确说明只返回部分结果。
- `no_data`：查询成功但结果为零行。
- `completed`：查询成功且通过结果校验。

生成 SQL、健康检查成功、模型说“已查询”和 HTTP 200 都不是业务数据结果。

### 6. 结果核验

根据指标合同执行最小必要核验：

- 日期是否落在请求窗口内，是否误把创建时间、付款时间、审核时间、出库时间或生产日期混用。
- 结果粒度是否唯一，是否因 Join 倍增；检查总行数、重复业务键和关键字段空值。
- 数量分项之和是否等于总量；订单明细数量与订单数是否使用了正确的去重键。
- 箱数、重量、吨数是否按 SKU 级箱规/净重换算，不能把 SKU 净重误当数量再相乘一次。
- 库存：在库、锁定、冻结、销售占用、调拨占用、采购在途、调拨在途的展示和计算必须区分；调拨占用是否剔除只按当前合同执行。
- 周转：分子库存快照和分母销售出库必须使用同一货主、仓库、SKU、成品范围和单位；日均分母除以完整自然日数。
- 明细金额、订单金额和商品金额不能在 SKU 明细上重复累计；需要汇总金额时先确定金额归属粒度。

发现异常时，给出“异常值、影响范围、最可能原因、是否影响结论、建议复核字段”，不要默默修正源数据。

## 高频业务口径提醒

以下是取数时优先核对的风险点，不是无条件硬编码规则：

- **销售出库**：核对完成状态、出库时间、出库明细数量和销售类型；不要把待出库分配量当成已出库。
- **订单数量**：订单头与明细一对多，通常按订单号去重；一个订单可能有多个退货单，退货件数需明确是订单总退货还是某一售后单。
- **库存**：以 `(货主, 仓库, SKU)` 为核心键，先聚合库存表；可用数量、分配数量和汇总数量不是同义字段。
- **在途**：采购在途与调拨在途分开算，分别核对计划、实收、实发、状态和收发仓；不要把调拨出库、调拨在途和调拨占用重复相加。
- **渠道**：`biz_channel`、店铺类型、平台编码、渠道细分枚举可能是不同层级；使用合同指定字段，不能看到“线上/线下”就替代渠道细分。
- **履约类型**：`2C`/`2B` 是发货条款维度；本项目已确认 `terms_of_shipment='20'` 表示 2C，非 `20` 表示 2B。它不等于客户渠道、`channel_code` 或订单请求数量。只有用户本轮明确提到 2C/2B 时才加入该范围条件。
- **DMS**：核对订单创建、付款、审核、出库时间和逻辑删除；积分兑换、普通销售、手工单、小程序单不是同一订单口径。
- **生产日期库存**：先明确是库存现状还是历史快照；“近两个月生产日期”应定义日期边界、库存状态和可用数量。
- **销售省区/客户经理**：省区可能来自省/市映射表，客户经理可能来自订单字段或员工表；Join 后先检查一对多和未匹配客户。

## 回答格式

对用户只输出业务可用信息：

1. 一句话说明统计口径、时间和单位。
2. 给出结果或结构化选择题。
3. 如有异常，单独列出影响和复核建议。
4. 如查询失败，说明失败类型和下一步，不伪造数字。

不要把 SQL、数据库凭据、原始结果行、审计内容、内部知识候选或模型私有推理写入对外文件。需要给开发人员排查时，只给脱敏后的表级、字段级和状态级信息。

## 维护规则

本 Skill 只描述取数方法，不替代项目语义合同。新增或纠正口径时，应更新对应的 `metrics/*.yaml`、`sources/**/*.yaml`、黄金问题和发布清单，经校验和业务审核后再生效。历史 SQL 只能作为迁移证据，不能直接复制为新默认口径。

详细决策记录模板见 [references/decision-contract.md](references/decision-contract.md)。
